# 数据模型与仓储

> 核心业务的数据契约：8 张表、对应 repo 与跨进程 IPC 通道清单。迁移文件在 `resources/drizzle/`（`npx drizzle-kit generate` 生成，随包 asarUnpack）。用量聚合表与看板口径详见 `../app/04-统计看板.md`。

## 表结构（`src/main/src/db/schema/`）

| 表 | 文件 | 用途 | 关键列 |
|----|------|------|--------|
| `providers` | `provider.ts` | 上游 AI 提供商（protocol 决定接口协议） | `id`(nanoid pk)、`name`、`protocol`(`openai`/`openai-responses`/`anthropic`，默认 `openai`)、`kind`(**可空**，内置提供商类型 `zai`/`opencode`/`deepseek`/`siliconflow`/`openai`，null = 自定义，见 `../app/10-内置提供商.md`)、`base_url`、`api_key`、`quota_strategy_id`(**可空**，绑定的余量策略 id，见 `../app/11-余量查询.md`)、`strategy_config`(**可空**，策略附加配置 JSON：cookie/token/区域等)、`enabled`、`archived_at`(**可空**，非空 = 已归档，见「归档（假删除）机制」)、`created_at`/`updated_at` |

| `request_logs` | `log.ts` | 请求详细日志（**行保留最近 7 天、正文只留 12~24 小时**；含标头；两阶段落库，见「日志保留策略」） | `request_id`(UUID，**unique 索引**，pending 行回填关联键)、`log_date`(YYYY-MM-DD，由请求时间推导，清理依据，有索引)、`started_at`(请求时间)、`finished_at`(**可空**，null = 进行中)、`public_model`、`provider_name`、`upstream_model`、`client`(**可空**，来源客户端标识 = user-agent 首个 token 的 `/` 前部分，只留名称不留版本；请求未携带 UA 与上线前的历史行为 null，见 `../app/04-统计看板.md`)、`provider_id`/`model_id`(**可空**，改名定位用，见「删除 / 改名与历史数据」)、`path`(上游实际请求路径，本地拦截时为客户端入口路径)、`status`(**可空**，null = 进行中)、`duration_ms`(**可空**)、`stream`、`prompt/completion/reasoning/cache_read/cache_write/unrecognized/total_tokens`、`request_body`、`request_headers`(脱敏)、`response_body`(流式为全部 SSE 文本)、`response_headers`(剔除 set-cookie)、`error`、`retry_trace`(**可空**，2026-09-23 起：负载均衡改道前的失败尝试 `[{provider,status,error,at}]` JSON，不额外占日志行，见 `../app/15-负载均衡与故障转移.md`) |
| `usage_daily` | `usage.ts` | 每日用量聚合（**永久保留**），看板的日粒度数据源 | 联合主键 `(date, provider_name, public_model)`、`provider_id`/`model_id`(**可空**，改名定位用，见「删除 / 改名与历史数据」)、`request_count`、`success_count`、`fail_count`、`duration_ms`、`prompt/completion/reasoning/cache_read/cache_write/unrecognized/total_tokens` |
| `usage_hourly` | `usage.ts` | 小时用量聚合（**7 天**，惰性清理），看板的小时粒度数据源 | 联合主键 `(hour_key, provider_name, public_model)`（`hour_key` 为 `YYYY-MM-DDTHH`，有索引）、`provider_id`/`model_id`(同上，可空)、列同上 |
| `quota_plugins` | `quota.ts` | 外置余量策略（用户 JS 脚本），见 `../app/11-余量查询.md` | `id`(pk)、`name`、`script`(脚本文本)、`enabled`、`archived_at`(**可空**，假删除 + 事务内解绑提供商)、`created_at`/`updated_at` |
| `quota_snapshots` | `quota.ts` | 余量快照（每提供商一行 UPSERT） | `provider_id`(pk)、`snapshot`(QuotaSnapshot JSON，**失败时保留旧值**)、`error`(可空，最近失败原因)、`queried_at` |

`usage_daily` 与 `usage_hourly` 在 schema 中共用 `usageColumns` 展开，**列集合完全一致**，仅时间桶键与粒度不同。

## 归档 / 改名与历史数据

历史表（`request_logs` / `usage_daily` / `usage_hourly`）**只存请求发生时的名字快照**，不持有指向 `providers` / `models` 的外键。这带来两个方向相反的性质：

| 操作 | 对历史的影响 | 机制 |
|------|--------------|------|
| 归档提供商 / 模型映射 | **不受影响**：历史统计与日志照常显示旧名、照常可筛选 | 三张历史表无外键，归档只写配置表的 `archived_at` 状态位，一行都不删 |
| 修改配置里的名字 | **跟随改名**：历史行的名字列被同步改写，同一实体不裂成两组 | 按写入时一并落库的 `provider_id` / `model_id` 精确圈定并改写（`renameRepo.ts`） |

### 归档（假删除）机制

提供商与模型映射**只能归档、不能删除**（2026-09-18 起；`removeProvider` / `removeModelMapping` 与 `provider:remove` / `model:remove` 通道已移除）。归档 = 写 `archived_at`（epoch ms，NULL = 未归档），与 `enabled` **正交**（归档不改 enabled，恢复后原启用状态回来）：

| 规则 | 行为 |
|------|------|
| 对外不可见 | `GET /v1/models` 过滤掉归档映射**与**归档提供商下的映射；命中归档映射的请求 404 `model_archived`（`The model 'X' has been archived`），禁用仍是 404 `model_not_found` 的不区分口径 |
| 级联归档 | 归档提供商在同一事务内连带归档其下**未归档**映射（只写 `archived_at IS NULL` 的行，先前单独归档过的映射保留自己的时间戳），不留「提供商已归档、映射仍对外可见」的中间态 |
| 恢复互不牵连 | 恢复提供商**只恢复自身**，映射保持归档，需在模型页逐个恢复；恢复映射时若提供商仍归档，该映射依旧不可用（列表与路由另按 `providers.archived_at` 拦截），UI 提示「请先恢复提供商」 |
| 归档即冻结 | `updateProvider` / `updateModelMapping` 命中归档行直接抛错；UI 上归档行不渲染编辑与启停入口。状态翻转只经 `archive*` / `restore*` |
| 名字不释放 | 0007 起 `public_name` 不再全局唯一，名字所有权改由**渠道行**承载：`(public_name, provider_id)` 组合被归档行占用时 `ensureChannelAvailable` 拒绝重建（「已存在同名归档渠道，请先恢复」）；该名下**全部**行都已归档时 `ensureGroupUsable` 拒绝再挂任何渠道（「对外名已归档，请先恢复或改名」） |
| 列表默认隐藏 | 两个管理页都有「显示已归档」开关（默认关、仅前端过滤、不落库），归档行置灰且只留「恢复」 |

**为什么从物理删除改成归档**（推翻本文档此前的「不需要软删除」论证）：旧论证针对的是「防止历史名变 NULL / 空白」，那个目标物理删除本已达成（历史表无外键、读路径不 join 主表）。但物理删除另有两处真实代价，归档正好堵住：

1. **id 断链**：历史行的 `provider_id` / `model_id` 会变成无主 id，`renameRepo` 的改名跟随再也圈不到它们。归档保留实体行，id 始终指得回本行。
2. **名字被释放**：删掉叫 X 的供应商后可以马上再建一个同名 X，两段历史并进同一聚合行（见下文「已知限制」）。归档占住名字，这条路径不再可达。

旧论证提到的三条代价依旧成立，只是现在值得付：归档行占着 `public_name` 的唯一索引；所有读路径都要补 `archived_at IS NULL` 过滤，其中 `modelRepo.findMapping()` / `proxyRouter.handleListModels()` 漏一处就是对外泄漏 —— 现由 `MappingRoute` 的 `mappingArchivedAt` / `providerArchivedAt` 两字段统一承载这两个读路径。

### 改名改写的实现（`renameRepo.ts`）

- **按 id 而非按名圈定**：`providers.name` 允许重名（同名两家各有一条历史），按名字改写会误伤另一家。
- **只改名字列，不改 `upstream_model`**：那是「这个请求实际发给了谁」的事实记录，改名不是改变历史事实。
- **改绑 `providerId` 不触发改写**：历史请求确实发给了旧供应商，改掉就是伪造历史。同理，`upstreamName`（上游模型名）变化不涉及分组键，无需改写。
- **聚合表必须走合并**：`usage_daily` / `usage_hourly` 的主键含名字列，目标名可能已被占用（例如撞上**已删除供应商**留下的永久历史行），裸 `UPDATE` 会违反主键。因此走 `INSERT ... ON CONFLICT DO UPDATE`：无冲突行以新名插入、冲突行逐列累加合并，再删掉旧名源行。
- **源行经临时表中转**：不能直接 `INSERT INTO t SELECT ... FROM t` —— 同一张表边读边写时，SQLite 不保证读取看不到本语句刚插入的行，计数有被重复累加的风险。规避方式是把源行先抄进临时表 `_rename_rows`、在临时表里改名、再从临时表插入目标，最后删源行（全在同一事务内，任一步失败整体回滚）。
- **插入语句的 `SELECT` 必须带一个恒真 `WHERE`**：`INSERT ... SELECT` 后面直接接 `ON CONFLICT` 时，SQLite 会把 `ON` 解析成 join 的 `ON` 子句，在 prepare 阶段报 `near "DO": syntax error`（官方文档 "Parsing Ambiguity" 给的解法就是补一个 `WHERE`，哪怕恒真）。2026-09-16 引入临时表方案时漏了这条，导致模型与供应商改名**全部**失败（事务回滚、无脏数据），2026-09-23 补上。
- **集合式语句，不做 JS 行循环**：逐行改写会把几万行变成几万次语句往返，在同步驱动上直接卡住主进程。
- **单事务**：`providerRepo.updateProvider` / `modelRepo.updateModelMapping` 把「改配置 + 改历史」放进一个事务，否则中途失败会留下裂成两组的统计。旧名**以库中值为准**（不信入参）—— 列表页行内启停会把整行原样回传，按入参判断会在每次启停时白扫历史表。

### 性能与已知限制

- **同步阻塞主进程**：`better-sqlite3` 是同步 API，改写期间渲染层 IPC 与托盘刷新都在排队。典型本地用量下是几十毫秒量级，弹窗保存按钮的 `:loading` 足以覆盖；`request_logs` 的 `provider_id` 没有索引，是这次操作里最重的一步。若哪天觉得慢，逃生口是加 `idx_request_logs_provider`（代价是每次请求写入多维护一个索引）。
- **同名供应商的历史行已被融合**：分组键是名字，两家同名供应商的请求会累加进**同一行**，此时 `provider_id` 只记首次写入者。给其中一家改名会带走整行 —— 这是允许重名的代价，介意就别起同名。
- **本次改动之前写入的历史行没有 id**：无法被改名跟随。`accumulateUsage` 的冲突累加里对 id 用 `coalesce` 补空，这些老行会在下次累加时获得 id、恢复可跟随。
- **提供商改名撞上归档同名仍会合并**：`providers.name` 本就允许重名，把现存提供商改成某个**已归档**提供商的名字是允许的，两段历史随后并入同一分组（主键含名字，无 id 维度）。模型映射没有这条路径 —— 改成已存在的组名（含归档行）会被 `renameModelGroup` 的占用检查拒绝（0007 起这条约束由应用层守，不再是 `public_name` 的数据库唯一索引）。

## 日志保留策略（定时任务：行 7 天 + 正文 12~24 小时）

- **定时清理（行）**：`logRepo.cleanupExpiredLogs()` 执行 `DELETE FROM request_logs WHERE log_date < 边界日`（边界 = 今天 −6 天，即保留含当天在内最近 7 天）。由 scheduler 域的 `log:retention` 任务每日 04:30 调用（启动时补跑一次，见 `../app/13-定时任务.md`）——**不再挂在写日志路径上**：写路径触发的频率实际由流量决定，空闲的库反而永不清理。
- **定时清理（正文，2026-09-19）**：同一函数里接着调 `sweepExpiredBodies()` —— 把 `started_at` 早于 `LOG_BODY_RETENTION_HOURS`（12 小时，`src/common/constants.ts` 三端共用）的行的 `request_body` / `response_body` 置空，**行、标头与统计信息照旧保留 7 天**。原因：正文是体积的主要来源（流式响应会把整段 SSE 文本落库，是表里唯一的 MB 级列；本机实测该库到过 2.8 GB + 2.7 GB WAL），而日志列表、三组筛选项、模型速度折线与来源统计只读元数据列。标头不清 —— KB 级体积，排查时仍有用。
- **正文实留 12~24 小时**：清扫每天固定跑一次，故最早的一份正文存活 12 小时（写完赶上下一轮清扫）、最晚 24 小时。（改造前挂在写路径上按天节流，空闲一天会拖到 36 小时。）想换成稳定的 24~25 小时，把 cron 与边界常量一起改即可，清扫代码不用动。
- **分批推进**：正文清扫按 id 递增（id 自增即时间序，越过边界后最后一批自然清空退出）分批，单批 200 行、批间停顿 50ms 让出事件循环 —— 首次启用要清掉此前积累的多天正文，只会表现为后台慢慢跑，不会一次大 UPDATE 卡住主进程（写放大也摊薄到整个清扫过程）。游标在进程内有效，重启后从最小 id 重新走一遍（此时旧行正文已是空，只多一次元数据扫描）。`cleanupExpiredLogs()` 返回的 Promise 在清扫结束时 resolve，调度侧据此判定本轮结束（防重叠触发）；中途出错由 `[scheduler]` 统一记日志，游标停在最后成功批次，下次触发或重启后继续。
- **文件不会自动变小**：SQLite 删除行 / 置空大字段只把页放回 freelist 供后续写入复用，文件本身停在高水位线。**WAL 已由 `db:wal-checkpoint` 任务每日自动 `wal_checkpoint(TRUNCATE)`**（被读事务占住时本轮跳过）；文件本身要真正缩容（回收 freelist）仍需在**应用关闭后**执行一次 `sqlite3 ~/.ai-router/db/ai-router.db "VACUUM;"`（需要与结果文件相当的临时空间）。
- **用量累加**：`usageRepo.accumulateUsage()` 用 `onConflictDoUpdate` 实现 `原值 + excluded.x` 的原子累加，只增不减；日表永久保留，小时表的超窗桶由 `usage:retention` 任务每日清理（改造前挂在每次累加写入的末尾，让写路径白白多背一条 DELETE）。**统计口径与日志保留期无关**：概览看板、用量明细、托盘全部读聚合表，砍保留期不影响任何数字；只有「模型速度」与「来源 Agent 请求数」两张图读日志表，它们只依赖元数据列，因此也不受正文清空影响（见 `../app/04-统计看板.md`）。

## 日志两阶段落库（进行中状态）

日志写入拆为两次，让日志页能即时看到「进行中」的请求：

| 阶段 | 方法 | 时机 | 写入内容 |
|------|------|------|----------|
| 开始 | `logRepo.startLog()` ← `proxyLog.startRequest()` | 路由命中、发起上游请求**之前** | pending 行：`request_id`/`log_date`/`started_at`/`public_model`/`provider_name`/`upstream_model`/`client`/`path`/`stream`/`request_body`/`request_headers`；`finished_at`/`status`/`duration_ms` 留 **null** |
| 结束 | `logRepo.recordLog()` ← `proxyLog.recordRequest()` | 响应结束（含失败 / 客户端中断） | 以 `request_id` 为冲突键 **upsert**，回填 `finished_at`/`status`/`duration_ms`/全部 token 列 / `response_body`/`response_headers`/`error` |

- **null 即「进行中」**：未采用 `status=0` 之类的哨兵值，避免污染「失败」筛选口径。
- **兼容单阶段写入**：未走 `startLog` 的同步拦截分支（401 鉴权失败、400 非法 body / 缺 model、404 模型未找到）无匹配行时 upsert 退化为 INSERT，与改造前完全等价。
- **用量聚合不参与**：`usage_daily`/`usage_hourly` 仍**只在结束阶段**累加，pending 行不计入，统计口径不变。
- **残留收口**：应用退出 / 崩溃时 pending 行会永远停在进行中，`markPendingInterrupted()` 在启动时把 `finished_at IS NULL` 的行统一标记为 `status=499`、`error='服务中断'`、耗时按 `now - started_at` 计算。**注意**：这些请求从未写入聚合表，故「日志条数」会略多于「统计请求数」，两者对不上时以此为准。
- **写入观察者**：`logRepo.onLogWritten(cb)` 在 `startLog`/`recordLog` 落库后触发，供 `logIpc.ts` 广播 `log:changed`（db 层不依赖 electron）。

## repo 清单（`src/main/src/db/repo/`）

| 文件 | 职责 |
|------|------|
| `providerRepo.ts` | list/create/update/archive/restore（**无物理删除**）；`listProviders()` 附子查询 `modelCount`（不含归档映射，语义为「可用模型数」；**Drizzle 坑**：`sql` 模板内插值的列在单表查询中会丢表名前缀，相关子查询引用外层列须用 `sql.raw('"providers"."id"')` 显式限定，否则 `"provider_id" = "id"` 都落在子查询的 `models` 作用域、恒为 0）；`archiveProvider()` 单事务级联归档其下未归档映射；`restoreProvider()` 只恢复自身；`updateProvider()` 改名时事务内同步改写历史（`applyProviderRename`），命中归档行抛错；四个写操作均调用 `modelRepo.invalidateMappingCache()`——`MappingRoute` 是联表结果，提供商侧写入（改名/换 Key/baseUrl/协议/启停/归档）同样影响代理路由缓存 |
| `modelRepo.ts` | 渠道级 list/create/update/archive/restore（**无物理删除**；`create/update` 前 `ensureChannelAvailable` 校验 `(public_name, provider_id)` 组合，撞归档行给专门文案）＋ **组级 `renameModelGroup` / `setModelGroupEnabled` / `archiveModelGroup` / `restoreModelGroup`（2026-09-23，同名全部行的单事务批量写；改名对每个渠道行 id 各调一次 `applyModelRename`）**；`create` 另有 `ensureGroupUsable`（整组已归档则拒挂渠道）；`updateModelMapping()` **不再接受 `publicName`**（名字不属于渠道，改名走组级）；`findRoutes(publicName)` 一次联表返回该名下**全部渠道**的代理路由 `MappingRoute[]`（含提供商 protocol/baseUrl/apiKey/enabled + 渠道 `modelId` + 双方归档时间），选择与故障转移见 `../app/15-负载均衡与故障转移.md`——**带 lru-cache 路由缓存（2026-09-19）**：代理热路径每请求都查，惰性填充、只缓存命中行（未映射名不占缓存），LRU max 1000 仅作防膨胀保险，不设 TTL（配置数据本进程是唯一写者，写时失效即一致），本 repo 与 providerRepo 的任一写操作调 `invalidateMappingCache()` 整体失效（同 settingRepo 写时失效口径；缓存对象只读，调用方不得修改）；`listModelMappings()` 联表带 `providerName` / `providerArchivedAt`（**不缓存**：/v1/models 与管理页 IPC 都是冷路径，管理页新鲜度优先）；命中归档行抛错 |
| `renameRepo.ts` | 改名时的历史引用同步：`applyProviderRename()` / `applyModelRename()` 按 id 集合式改写 `usage_daily` / `usage_hourly`（冲突累加合并）与 `request_logs`；导出写入侧共用的 `HistoryRef` 契约 |
| `settingRepo.ts` | `ensureServiceDefaults()`（首次初始化：端口 8910、生成 `sk-` + nanoid(32) Key、enabled=1）、`getServiceConfig()`、`saveServiceConfig()`、`regenerateApiKey()`；**服务配置带缓存**（2026-09-17 引入，2026-09-19 统一换 lru-cache 单值槽位 max 1）：鉴权/出站代理每请求都读，`getServiceConfig()` 惰性加载直读缓存，三个写操作（save/regenerate/ensure 补默认）后失效缓存、下次读时重查——settings 表无 repo 之外的访问点，缓存封装在 repo 内部即无失效遗漏风险；**通用偏好读写（2026-09-19）**：`getSetting(key)` / `setSetting(key, value)` 供渲染层 UI 偏好走 setting 域 IPC 存取（读频低不缓存，写后同样清 service 配置缓存防键交叉） |
| `logRepo.ts` | `startLog()`（pending 行）、`recordLog()`（按 `request_id` upsert 回填，logDate 由 startedAt 推导）、`cleanupExpiredLogs()`（async，由 `log:retention` 调度任务调用）、`markPendingInterrupted()`（启动收口残留，由 scheduler 启动时调用）、`onLogWritten()`（写入观察者）、`listLogs(query)`（状态 全部/成功2xx/失败非2xx且已结束 + 供应商/模型/来源筛选，`started_at` 倒序分页）、`listFilterOptions()`（去重供应商/模型/来源）、`getLogDetail(id)`（全量详情）、`clearAllLogs()`（**异步分批**：以发起时刻最大 id 为上界按 id 升序逐批删，批间让出事件循环——执行期间代理照常响应、期间新写入的日志不受影响；结束后正文清扫游标归零）、`getTodayStats()` |
| `usageRepo.ts` | `accumulateUsage()`（日/小时同事务累加 + 小时表清理）、`resolveRange()`/`activityDaysOf()`（维度 → 桶序列 / 热力图窗口）、`queryUsageOverview()`（看板唯一入口：总计 + 供应商/模型拆分 + 时间序列 + 活跃度）、`queryUsageFilterOptions()`、`listUsageByRange(start, end)`（明细表） |
| `quotaRepo.ts` | 外置策略 `listQuotaPlugins/createQuotaPlugin/updateQuotaPlugin/archiveQuotaPlugin`（命中归档行抛错；归档单事务连带解绑提供商）+ 快照 `listQuotaSnapshots()` / `saveQuotaResult()`（成功覆盖 snapshot 并清 error；失败保留旧 snapshot 只更新 error）；策略脚本 eval 装载在 `../app/11-余量查询.md` 的服务层 |
| `clientRepo.ts` | `queryClientStats()`（来源 Agent 请求数，固定近七天）、`queryAgentProviderFlow()`（Agent × 提供商交叉流量，固定近七天，桑基图用）：与 `speedRepo.ts` 同属「**直接实时聚合 `request_logs`**」的统计项，不读用量聚合表（聚合表无来源维度）。口径与取舍见 `../app/04-统计看板.md` |

## IPC 通道（`src/main/src/ipc/`，在 `registerIpc.ts` 聚合）

| 域 | 通道 | 说明 |
|----|------|------|
| provider | `provider:list/create/update/archive/restore` | create/update 入参 `ProviderInput`（有 `id` 为更新，`protocol` 枚举校验，`kind` 可选枚举校验），返回新实体 id；archive/restore 入参只有 `id`（归档连带归档其下未归档映射、恢复只恢复自身） |
| model | `model:list/create/update/archive/restore` | 同上；重名抛错（文案含「已存在」或「已被归档的映射占用」）；archive/restore 入参只有 `id` |
| service | `service:getConfig/saveConfig/regenerateKey/getStatus` | **saveConfig 保存后自动 `restartProxyServer()`** 并返回新 `ServiceStatus`；regenerateKey 只换库中 Key（配置走 repo 缓存、写时失效，代理侧立即生效，无需重启） |
| setting | `setting:get/set` + 推送 `setting:changed { key }` | **通用键值偏好通道（2026-09-19）**：渲染层 UI 偏好（如看板卡片布局 `dashboard.layout`，见 `../app/12-看板卡片配置.md`）的 JSON 序列化存取；set 后向**所有窗口**广播，另一窗口实时同步 |
| log | `log:list/filterOptions/getDetail/clearAll/todayStats` + 推送 `log:changed` | `list` 入参 `LogListQuery`（状态/供应商/模型/来源 + 分页，IPC 层归一化非法值）；`log:changed` 由 `logIpc.ts` 订阅 `onLogWritten` 后 **300ms 合并广播**给全部窗口，驱动日志页实时刷新 |
| usage | `usage:overview/filterOptions/listByRange/modelSpeed/clientStats` | `overview` 入参 `UsageQuery`（range 枚举白名单 + 可选筛选），返回 `UsageOverview`；`modelSpeed` 与 `clientStats` 均无入参（窗口固定近七天），是仅有的两个实时聚合 `request_logs` 的统计通道 |
| quota | `quota:list/refresh/strategies` | `list` 纯读库（绑定策略的提供商 + 快照，零出站）；`refresh(providerId?)` 出站刷新后返回新列表；`strategies` 返回注册表目录（内置只读 + 外置含启停），架构见 `../app/11-余量查询.md` |
| quotaPlugin | `quotaPlugin:list/create/update/archive` | 外置脚本策略管理：create/update 前先 eval 校验脚本（失败中文报错不落库），成功后重载注册表；archive 假删除 + 事务解绑提供商 + 注册表移除 |
| tray | `tray:hide/openMain` + 推送 `tray:shown` | 托盘统计面板的收起与跳转主窗口；`tray:shown` 在每次弹出面板时推送，驱动渲染层刷新 |

## 跨进程契约（三端共享）

- 契约类型统一定义在 `src/common/types/`（`provider.ts` / `model.ts` / `service.ts` / `log.ts` / `usage.ts` / `quota.ts` / `dashboard.ts`），main / preload / renderer 经 `@common/types` 引用。
- 渲染层全局类型镜像在 `src/renderer/src/vite-env.d.ts` 的 `Window.preload`（手写，与 `src/preload/index.ts` 组装保持同步）。
- main → renderer 推送：
  - `server:status`（`ServiceStatus`），由 `proxyServer.ts` 在状态变化时经 `webContents.send` 广播，preload `serviceApi.onStatusChanged` 订阅。
  - `log:changed`（无载荷），由 `logIpc.ts` 在日志落库 / 回填后广播（300ms 合并），preload `logApi.onChanged` 订阅；订阅方需自行防抖并在不必要时跳过重查。
  - `setting:changed`（`{ key }`），由 `settingIpc.ts` 在通用键值保存后广播给全部窗口，preload `settingApi.onSettingChanged` 订阅（另一窗口据此重读配置，如看板卡片布局跨窗口同步）。

## 新增表的流程备忘

1. `src/main/src/db/schema/<域>.ts` 定义表 → `schema/index.ts` re-export
2. `npx drizzle-kit generate`（drizzle `run()` 底层只支持单语句，禁止手写多语句 DDL）
3. `src/main/src/db/repo/<域>Repo.ts` 数据操作 → `src/main/src/ipc/<域>Ipc.ts` 参数校验与转发 → `registerIpc.ts` 聚合
4. `src/preload/src/modules/<域>/` 薄桥 → `preload/index.ts` 组装 → `vite-env.d.ts` 补类型
