# 数据模型与仓储

> 核心业务的数据契约：6 张表、对应 repo 与跨进程 IPC 通道清单。迁移文件在 `resources/drizzle/`（`npx drizzle-kit generate` 生成，随包 asarUnpack）。用量聚合表与看板口径详见 `../app/04-统计看板.md`。

## 表结构（`src/main/src/db/schema/`）

| 表 | 文件 | 用途 | 关键列 |
|----|------|------|--------|
| `providers` | `provider.ts` | 上游 AI 提供商（protocol 决定接口协议） | `id`(nanoid pk)、`name`、`protocol`(`openai`/`openai-responses`/`anthropic`，默认 `openai`)、`base_url`、`api_key`、`enabled`、`created_at`/`updated_at` |
| `models` | `model.ts` | 模型映射（渠道）：对外名 ↔ 上游名 | `id`(pk)、`provider_id`(fk→providers, **onDelete cascade**)、`public_name`(**unique**)、`upstream_name`、`enabled` |
| `settings` | `setting.ts` | 键值配置 | `key`(pk)、`value`；现有键 `server.port` / `server.apiKey` / `server.enabled` / `server.proxyUrl`（上游请求代理，空串直连） |
| `request_logs` | `log.ts` | 请求详细日志（**最近 7 天**，含正文与标头；两阶段落库） | `request_id`(UUID，**unique 索引**，pending 行回填关联键)、`log_date`(YYYY-MM-DD，由请求时间推导，清理依据，有索引)、`started_at`(请求时间)、`finished_at`(**可空**，null = 进行中)、`public_model`、`provider_name`、`upstream_model`、`provider_id`/`model_id`(**可空**，改名定位用，见「删除 / 改名与历史数据」)、`path`(上游实际请求路径，本地拦截时为客户端入口路径)、`status`(**可空**，null = 进行中)、`duration_ms`(**可空**)、`stream`、`prompt/completion/reasoning/cache_read/cache_write/unrecognized/total_tokens`、`request_body`、`request_headers`(脱敏)、`response_body`(流式为全部 SSE 文本)、`response_headers`(剔除 set-cookie)、`error` |
| `usage_daily` | `usage.ts` | 每日用量聚合（**永久保留**），看板的日粒度数据源 | 联合主键 `(date, provider_name, public_model)`、`provider_id`/`model_id`(**可空**，改名定位用，见「删除 / 改名与历史数据」)、`request_count`、`success_count`、`fail_count`、`duration_ms`、`prompt/completion/reasoning/cache_read/cache_write/unrecognized/total_tokens` |
| `usage_hourly` | `usage.ts` | 小时用量聚合（**7 天**，惰性清理），看板的小时粒度数据源 | 联合主键 `(hour_key, provider_name, public_model)`（`hour_key` 为 `YYYY-MM-DDTHH`，有索引）、`provider_id`/`model_id`(同上，可空)、列同上 |

`usage_daily` 与 `usage_hourly` 在 schema 中共用 `usageColumns` 展开，**列集合完全一致**，仅时间桶键与粒度不同。

## 删除 / 改名与历史数据

历史表（`request_logs` / `usage_daily` / `usage_hourly`）**只存请求发生时的名字快照**，不持有指向 `providers` / `models` 的外键。这带来两个方向相反的性质：

| 操作 | 对历史的影响 | 机制 |
|------|--------------|------|
| 删除提供商 / 模型映射 | **不受影响**：历史统计与日志照常显示旧名、照常可筛选 | 三张历史表无外键，删除只碰配置表（`providers` → `models` 的 cascade 只删映射，不碰历史） |
| 修改配置里的名字 | **跟随改名**：历史行的名字列被同步改写，同一实体不裂成两组 | 按写入时一并落库的 `provider_id` / `model_id` 精确圈定并改写（`renameRepo.ts`） |

### 为什么删除不需要软删除

一旦把「统计要稳」当成删除的约束，就会想给 `providers` / `models` 加 `deletedAt`。这里**不需要**，而且软删除反而更贵：

- 统计与日志的读取路径**完全不 join 主表**（`usageRepo` / `logRepo` 只用 `selectDistinct` 聚合表自身的名字列），所以删除不可能让历史名变成 NULL 或空白。
- `models.public_name` 是 **DB 级 unique**。一旦软删除，同名重建会撞唯一约束，必须把约束改成 `WHERE deleted_at IS NULL` 的部分索引。
- 所有读路径都要补 `deletedAt IS NULL` 过滤，其中 `modelRepo.findMapping()` **漏一处就是路由故障** —— 被软删的映射会被代理继续命中。

### 改名改写的实现（`renameRepo.ts`）

- **按 id 而非按名圈定**：`providers.name` 允许重名（同名两家各有一条历史），按名字改写会误伤另一家。
- **只改名字列，不改 `upstream_model`**：那是「这个请求实际发给了谁」的事实记录，改名不是改变历史事实。
- **改绑 `providerId` 不触发改写**：历史请求确实发给了旧供应商，改掉就是伪造历史。同理，`upstreamName`（上游模型名）变化不涉及分组键，无需改写。
- **聚合表必须走合并**：`usage_daily` / `usage_hourly` 的主键含名字列，目标名可能已被占用（例如撞上**已删除供应商**留下的永久历史行），裸 `UPDATE` 会违反主键。因此走 `INSERT ... ON CONFLICT DO UPDATE`：无冲突行以新名插入、冲突行逐列累加合并，再删掉旧名源行。
- **源行经临时表中转**：不能直接 `INSERT INTO t SELECT ... FROM t` —— 同一张表边读边写时，SQLite 不保证读取看不到本语句刚插入的行，计数有被重复累加的风险。规避方式是把源行先抄进临时表 `_rename_rows`、在临时表里改名、再从临时表插入目标，最后删源行（全在同一事务内，任一步失败整体回滚）。
- **集合式语句，不做 JS 行循环**：逐行改写会把几万行变成几万次语句往返，在同步驱动上直接卡住主进程。
- **单事务**：`providerRepo.updateProvider` / `modelRepo.updateModelMapping` 把「改配置 + 改历史」放进一个事务，否则中途失败会留下裂成两组的统计。旧名**以库中值为准**（不信入参）—— 列表页行内启停会把整行原样回传，按入参判断会在每次启停时白扫历史表。

### 性能与已知限制

- **同步阻塞主进程**：`better-sqlite3` 是同步 API，改写期间渲染层 IPC 与托盘刷新都在排队。典型本地用量下是几十毫秒量级，弹窗保存按钮的 `:loading` 足以覆盖；`request_logs` 的 `provider_id` 没有索引，是这次操作里最重的一步。若哪天觉得慢，逃生口是加 `idx_request_logs_provider`（代价是每次请求写入多维护一个索引）。
- **同名供应商的历史行已被融合**：分组键是名字，两家同名供应商的请求会累加进**同一行**，此时 `provider_id` 只记首次写入者。给其中一家改名会带走整行 —— 这是允许重名的代价，介意就别起同名。
- **本次改动之前写入的历史行没有 id**：无法被改名跟随。`accumulateUsage` 的冲突累加里对 id 用 `coalesce` 补空，这些老行会在下次累加时获得 id、恢复可跟随。
- **同名重建仍会合并**：删掉叫 X 的供应商、再新建一个也叫 X，新旧历史并到同一分组（主键含名字，无 id 维度）。

## 日志保留策略（无定时器，最近 7 天）

- **惰性清理**：`logRepo.cleanupExpiredLogs()` 执行 `DELETE FROM request_logs WHERE log_date < 边界日`（边界 = 今天 −6 天，即保留含当天在内最近 7 天）。**按天节流**：模块内记录 `lastCleanupDate`，同一天内重复调用直接返回，把「每请求一次 DELETE」降为「每天一次」；`main/index.ts` 启动时经 `cleanupLogsOnStartup()` 另调一次兜底（覆盖「窗口内无新请求」的场景）。
- **用量累加**：`usageRepo.accumulateUsage()` 用 `onConflictDoUpdate` 实现 `原值 + excluded.x` 的原子累加，只增不减；日表永久保留，小时表在累加时顺带清理超窗桶。

## 日志两阶段落库（进行中状态）

日志写入拆为两次，让日志页能即时看到「进行中」的请求：

| 阶段 | 方法 | 时机 | 写入内容 |
|------|------|------|----------|
| 开始 | `logRepo.startLog()` ← `proxyLog.startRequest()` | 路由命中、发起上游请求**之前** | pending 行：`request_id`/`log_date`/`started_at`/`public_model`/`provider_name`/`upstream_model`/`path`/`stream`/`request_body`/`request_headers`；`finished_at`/`status`/`duration_ms` 留 **null** |
| 结束 | `logRepo.recordLog()` ← `proxyLog.recordRequest()` | 响应结束（含失败 / 客户端中断） | 以 `request_id` 为冲突键 **upsert**，回填 `finished_at`/`status`/`duration_ms`/全部 token 列 / `response_body`/`response_headers`/`error` |

- **null 即「进行中」**：未采用 `status=0` 之类的哨兵值，避免污染「失败」筛选口径。
- **兼容单阶段写入**：未走 `startLog` 的同步拦截分支（401 鉴权失败、400 非法 body / 缺 model、404 模型未找到）无匹配行时 upsert 退化为 INSERT，与改造前完全等价。
- **用量聚合不参与**：`usage_daily`/`usage_hourly` 仍**只在结束阶段**累加，pending 行不计入，统计口径不变。
- **残留收口**：应用退出 / 崩溃时 pending 行会永远停在进行中，`markPendingInterrupted()` 在启动时把 `finished_at IS NULL` 的行统一标记为 `status=499`、`error='服务中断'`、耗时按 `now - started_at` 计算。**注意**：这些请求从未写入聚合表，故「日志条数」会略多于「统计请求数」，两者对不上时以此为准。
- **写入观察者**：`logRepo.onLogWritten(cb)` 在 `startLog`/`recordLog` 落库后触发，供 `logIpc.ts` 广播 `log:changed`（db 层不依赖 electron）。

## repo 清单（`src/main/src/db/repo/`）

| 文件 | 职责 |
|------|------|
| `providerRepo.ts` | CRUD；`listProviders()` 附子查询 `modelCount`；`updateProvider()` 改名时事务内同步改写历史（`applyProviderRename`） |
| `modelRepo.ts` | CRUD（`create/update` 前校验 `publicName` 唯一）；`findMapping()` 一次联表返回代理路由 `MappingRoute`（含提供商 protocol/baseUrl/apiKey/enabled + 映射 `modelId`）；`listModelMappings()` 联表带 `providerName`；`updateModelMapping()` 对外名变化时同步改写历史（`applyModelRename`） |
| `renameRepo.ts` | 改名时的历史引用同步：`applyProviderRename()` / `applyModelRename()` 按 id 集合式改写 `usage_daily` / `usage_hourly`（冲突累加合并）与 `request_logs`；导出写入侧共用的 `HistoryRef` 契约 |
| `settingRepo.ts` | `ensureServiceDefaults()`（首次初始化：端口 8910、生成 `sk-` + nanoid(32) Key、enabled=1）、`getServiceConfig()`、`saveServiceConfig()`、`regenerateApiKey()`；**服务配置带模块级缓存**（2026-09-17）：鉴权/出站代理每请求都读，`getServiceConfig()` 惰性加载直读缓存，三个写操作（save/regenerate/ensure 补默认）后失效缓存、下次读时重查——settings 表无 repo 之外的访问点，缓存封装在 repo 内部即无失效遗漏风险 |
| `logRepo.ts` | `startLog()`（pending 行）、`recordLog()`（按 `request_id` upsert 回填，logDate 由 startedAt 推导）、`cleanupExpiredLogs()`（按天节流）、`markPendingInterrupted()`（启动收口残留）、`onLogWritten()`（写入观察者）、`listLogs(query)`（状态 全部/成功2xx/失败非2xx且已结束 + 供应商/模型筛选，`started_at` 倒序分页）、`listFilterOptions()`（去重供应商/模型）、`getLogDetail(id)`（全量详情）、`clearAllLogs()`、`getTodayStats()` |
| `usageRepo.ts` | `accumulateUsage()`（日/小时同事务累加 + 小时表清理）、`resolveRange()`/`activityDaysOf()`（维度 → 桶序列 / 热力图窗口）、`queryUsageOverview()`（看板唯一入口：总计 + 供应商/模型拆分 + 时间序列 + 活跃度）、`queryUsageFilterOptions()`、`listUsageByRange(start, end)`（明细表） |

日期/时间桶口径统一走 `src/main/src/utils/date.ts`：`todayKey()`（本地时区 `YYYY-MM-DD`）、`dateKey(ms)`、`hourKey(ms)`（`YYYY-MM-DDTHH`）、`hourLabel()`/`dayLabel()`（图表刻度标签）。

## IPC 通道（`src/main/src/ipc/`，在 `registerIpc.ts` 聚合）

| 域 | 通道 | 说明 |
|----|------|------|
| provider | `provider:list/create/update/remove` | create/update 入参 `ProviderInput`（有 `id` 为更新，`protocol` 枚举校验），返回新实体 id |
| model | `model:list/create/update/remove` | 同上；重名抛错（文案含「已存在」） |
| service | `service:getConfig/saveConfig/regenerateKey/getStatus` | **saveConfig 保存后自动 `restartProxyServer()`** 并返回新 `ServiceStatus`；regenerateKey 只换库中 Key（配置走 repo 缓存、写时失效，代理侧立即生效，无需重启） |
| log | `log:list/filterOptions/getDetail/clearAll/todayStats` + 推送 `log:changed` | `list` 入参 `LogListQuery`（状态/供应商/模型 + 分页，IPC 层归一化非法值）；`log:changed` 由 `logIpc.ts` 订阅 `onLogWritten` 后 **300ms 合并广播**给全部窗口，驱动日志页实时刷新 |
| usage | `usage:overview/filterOptions/listByRange/modelSpeed` | `overview` 入参 `UsageQuery`（range 枚举白名单 + 可选筛选），返回 `UsageOverview`；`modelSpeed` 无入参（窗口固定近七天），是唯一实时聚合 `request_logs` 的统计通道 |
| tray | `tray:hide/openMain` + 推送 `tray:shown` | 托盘统计面板的收起与跳转主窗口；`tray:shown` 在每次弹出面板时推送，驱动渲染层刷新 |

## 跨进程契约（三端共享）

- 契约类型统一定义在 `src/common/types/`（`provider.ts` / `model.ts` / `service.ts` / `log.ts` / `usage.ts`），main / preload / renderer 经 `@common/types` 引用。
- 渲染层全局类型镜像在 `src/renderer/src/vite-env.d.ts` 的 `Window.preload`（手写，与 `src/preload/index.ts` 组装保持同步）。
- main → renderer 推送：
  - `server:status`（`ServiceStatus`），由 `proxyServer.ts` 在状态变化时经 `webContents.send` 广播，preload `serviceApi.onStatusChanged` 订阅。
  - `log:changed`（无载荷），由 `logIpc.ts` 在日志落库 / 回填后广播（300ms 合并），preload `logApi.onChanged` 订阅；订阅方需自行防抖并在不必要时跳过重查。

## 新增表的流程备忘

1. `src/main/src/db/schema/<域>.ts` 定义表 → `schema/index.ts` re-export
2. `npx drizzle-kit generate`（drizzle `run()` 底层只支持单语句，禁止手写多语句 DDL）
3. `src/main/src/db/repo/<域>Repo.ts` 数据操作 → `src/main/src/ipc/<域>Ipc.ts` 参数校验与转发 → `registerIpc.ts` 聚合
4. `src/preload/src/modules/<域>/` 薄桥 → `preload/index.ts` 组装 → `vite-env.d.ts` 补类型
