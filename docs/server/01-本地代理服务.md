# 本地代理服务

> 核心功能：监听 `127.0.0.1:<port>`，凭全局 API Key 对外提供 OpenAI 兼容服务，按模型映射反向代理到上游提供商。代码在 `src/main/src/server/`（Express 5；出站统一为 axios，实例与拦截器在 `upstreamHttp.ts`；CORS / 鉴权 / 路由组装在 `proxyRouter.ts`，转发与流式透传在 `proxyHandler.ts`）。对外仅暴露 `GET /v1/models` 与 `POST /v1/chat/completions`；上游协议为 `openai-responses` / `anthropic` 时在 `forwardRequest` 内转入 ai-sdk 转换路径，见 [02-协议适配与转换.md](./02-协议适配与转换.md)。

## 生命周期

- 启动：`main/index.ts` `whenReady` 中 `ensureServiceDefaults() → cleanupLogsOnStartup() → await startProxyServer()`（服务开关关闭时只更新状态、不监听）。
- 重启：渲染层「服务设置」保存端口/开关后，`serviceIpc` 的 `service:saveConfig` 内调用 `restartProxyServer()`。Key 变更无需重启（配置读 `settingRepo` 缓存、写时失效，保存即生效）。
- 退出：`app.on('will-quit')` → `stopProxyServer()`（`close` + `closeAllConnections`）。
- 端口占用（EADDRINUSE）不崩溃，状态置 `error` 并广播。

## 状态推送

`proxyServer.ts` 的 `updateStatus()` 在状态变化时 `BrowserWindow.getAllWindows().forEach(w => w.webContents.send('server:status', status))`；渲染层经 `window.preload.service.onStatusChanged(cb)` 订阅（通道 `server:status`，载荷 `ServiceStatus`）。

## 请求处理流程（`proxyRouter.ts` 组装，`proxyHandler.ts` 转发）

```
OPTIONS            → CORS 中间件直接 204 + 预检响应（其余响应统一 setHeader 放行来源）
鉴权中间件失败     → 401 {error:{type:'authentication_error', code:'invalid_api_key'}} + 记日志
GET  /v1/models    → 本地生成 {object:'list', data:[…]}（启用且未归档的映射，且所属提供商未归档；owned_by=提供商名）
POST /v1/chat/completions → express.json 解析 body(≤32MB) → 取 model 查映射 → 按协议分支
其余 method/path   → 404
```

中间件顺序：CORS → 鉴权 → 路由（`app.get('/v1/models')`、`app.post('/v1/chat/completions', express.json(...))`）→ 404 兜底 → 错误兜底中间件。转发路由的异常经 `.catch(next)` 进入错误兜底，任何分支都不向客户端抛异常。

1. **鉴权**：兼容 `Authorization: Bearer <key>` 与 `x-api-key` 两种头；Key 来自 `settingRepo.getServiceConfig()`（模块级缓存，写时失效）。
2. **映射**：`modelRepo.findMapping(publicName)` 一次联表返回 `MappingRoute`（上游模型名 + 提供商 protocol/baseUrl/apiKey + 双方 enabled + 双方归档时间）。映射或提供商任一**归档** → 404 `model_archived`（`The model 'X' has been archived`，归档是对客户端的正式下线宣告，明确告知）；映射或提供商任一**禁用** → 404 `model_not_found`（对外表现为模型不存在，不泄漏配置）。归档的级联/恢复语义见 `../data/01-数据模型.md`。
3. **协议分支**：`providerProtocol === 'openai'` → 纯透传；否则调 `protocol/convertHandler.ts` 的 `forwardConverted()`（见 [02-协议适配与转换.md](./02-协议适配与转换.md)）。
4. **转发（透传路径）**：`getUpstreamClient().post(baseUrl(去尾斜杠) + '/chat/completions' + 原 query)`（axios，`validateStatus` 全放行使非 2xx 也走正常透传）——上游端点固定，`baseUrl` 视为 API 根（可含 `/v1`、`/api/plan/v3` 等版本/路径前缀，由提供商配置页 help 提示）；**除 `model` 字段替换外请求体原样透传**；客户端请求头全量透传（UA、`x-request-id`、`x-session-id`、`anthropic-beta` 等业务头原样到达上游，见 `forwardHeaders.ts` 黑名单剥离），`authorization` 替换为上游 Key。
5. **响应透传**：
   - 非流式：读完上游 body 一次性回写（状态码 + content-type 原样）。
   - 流式（content-type 含 `text/event-stream`）：`writeHead` 后逐块 `res.write` 回写，`write` 返回 false 时等 `drain` 背压；客户端断开（`res.on('close')` 且未写完）时 `AbortController.abort()` 中断上游——请求阶段 axios 抛错记 499，流读取阶段监听 abort 销毁上游连接终止透传，均不再回写、日志记 status 499（`client aborted`，与转换路径一致），区别于真实上游失败的 502。
6. **usage 提取**（不阻塞透传）：非流式 `JSON.parse` 取 `usage`；流式用 `createSseUsageFeeder()` 按完整行解析 `data:` 行，取最后一个非空 `usage`（`[DONE]` 跳过）。`normalizeUsage()` 同时识别明细：`prompt_tokens_details.cached_tokens` → 缓存读、`completion_tokens_details.reasoning_tokens` → 思考、Anthropic 风格 `cache_read_input_tokens` / `cache_creation_input_tokens` 兜底；`total_tokens` 缺失时用 prompt+completion 补齐。
7. **全量采集与落库（两阶段）**：入口生成 `requestId`（UUID）；`path` 记**上游实际请求路径**（`baseUrl` 的路径前缀 + 端点，如 `/api/plan/v3/chat/completions`，经 `upstreamPathOf()` 取 URL 的 pathname+query；本地拦截无上游时记客户端入口路径）。**采集口径为「线上口径」（2026-09-16）：请求正文/标头 = 实际发给提供商的内容，响应正文/标头 = 提供商实际返回的内容**。透传路径：`model` 替换后才序列化出站正文，标头取 `buildForwardHeaders()` 产物经 `serializeOutboundHeaders()` 剔除 `authorization` / `x-api-key` / `cookie`（提供商 Key 不入库）后序列化；响应标头剔除 `set-cookie`；响应正文非流式为完整 JSON 文本、流式在逐块转发循环中累积全部 SSE 文本（不截断）。**未发起上游请求的同步拦截分支（401/400/404）请求侧记 null**。
   - **开始阶段**（路由命中、请求上游**之前**）：`proxyLog.startRequest()` → `logRepo.startLog()` 落一条 **pending 行**（`finished_at`/`status`/`duration_ms` 为 null），日志页据此立即显示「进行中」并实时计时。透传路径的 `stream` 先按客户端 `stream` 字段预估，结束时以实际上游 content-type 判定值回填；透传路径 pending 行即已带出站正文标头，转换路径出站报文由 SDK 惰性生成、pending 行先空待回填。
   - **结束阶段**（成功 / 失败 / 客户端断开）：统一调 `proxyLog.recordRequest()`，以 `request_id` 为冲突键 upsert 回填状态码、耗时、token 与响应正文标头，**并按状态码累加 `usage_daily` + `usage_hourly`**（请求数与耗时不分成败，token 仅成功请求计入——失败请求 tokens 不可信，详见 `../app/04-统计看板.md`）；非 2xx 时响应前 500 字符入 `error`。
   - **同步拦截分支不落 pending**：401（鉴权，位于 `express.json` 之前无请求正文）/ 400（body 非对象、缺 `model`）/ 404（模型未映射或禁用）直接由 `recordRequest()` 单次写入（upsert 退化为 INSERT），未知字段填 `-`。502（上游网络失败）因已过 `startRequest`，走回填。
   - 提供商未返回用量时一次性兜底估算：按请求正文估算 token（CJK 1 字 1 token、其余 4 字符 1 token）计入 `unrecognized_tokens` 并作为总计，日志与聚合共用该值。落库失败静默，不影响代理。
   - 应用退出 / 崩溃残留的 pending 行由启动时 `markPendingInterrupted()` 收口为 499「服务中断」，详见 `../data/01-数据模型.md`。

## 日志变更推送（日志页实时刷新）

`logRepo` 落库 / 回填后触发写入观察者 `onLogWritten`，`logIpc.ts` 订阅后经 **300ms 合并广播** `log:changed`（无载荷）到 `BrowserWindow.getAllWindows()`；渲染层用 `window.preload.log.onChanged(cb)` 订阅，日志页收到后 300ms 防抖重查，仅在「自动刷新开启 && 第 1 页 && 窗口可见」时才真正取数。30 秒轮询保留为兜底（推送丢失、窗口从后台恢复）。

## 错误格式

统一 OpenAI 风格，所有响应带 `access-control-allow-origin: *`：

```json
{ "error": { "message": "…", "type": "authentication_error | invalid_request_error | api_error", "code": "…" } }
```

| 场景 | 状态码 | type / code |
|------|--------|-------------|
| Key 错误 | 401 | `authentication_error` / `invalid_api_key` |
| body 非 JSON / 缺 model | 400 | `invalid_request_error` |
| body 超 32MB | 413 | `invalid_request_error` |
| 模型未映射/禁用 | 404 | `invalid_request_error` / `model_not_found` |
| 模型已归档（映射或所属提供商归档） | 404 | `invalid_request_error` / `model_archived` |
| 上游网络失败 | 502 | `api_error`；message 与日志 `error` 均为拦截器增强后的具体原因（格式 `底层原因: 中文提示`，如 `getaddrinfo ENOTFOUND api.x.com: 域名解析失败（baseUrl 错误或 DNS 不可用）`），映射表见 `upstreamHttp.ts` `NETWORK_HINTS` |
| 客户端断开（已 abort 上游） | 499（仅日志，不回写） | — |
| 请求进行中（仅日志，pending 行） | `status` 为 null | — |
| 应用退出残留的进行中请求 | 499（启动时由 `markPendingInterrupted()` 标记） | — |
| 上游返回 | 原样透传上游状态码与 body | — |

body 超 32MB / 非法 JSON 由 `express.json` 抛错（413 / 400），错误兜底中间件统一转上表 OpenAI 风格；非对象 body（数组/标量）在 `forwardRequest` 内拦截为 400。

## 注意事项

- 无请求总超时：长流式回答不设上限（axios `timeout: 0`），靠客户端断开驱动 abort。
- **出站统一走 `upstreamHttp.ts`（2026-09-17 替换 fetch）**：axios（Node http 适配器）实例按 `proxyUrl` 缓存重建（连接复用），`proxy: false` 屏蔽 `HTTP_PROXY` 等环境变量干扰；**响应拦截器统一增强网络层错误**——无 response 的 AxiosError 的 message 改写为「错误码: 底层 cause 原因: 中文提示」，两条转发路径 catch 到的都已是具体原因，不再出现裸「fetch failed」。
- **出站固定 `Accept-Encoding: identity`（禁用上游压缩）**：axios 在 `responseType: 'stream'` 下**不解压** gzip（与 undici fetch 的自动解压不同），压缩响应会以乱码入库并原样发给客户端；禁用后响应体/响应头均为提供商原样明文，日志记录、客户端透传、SSE usage 提取（`createSseUsageFeeder` 按明文行解析）才都成立。转发本机回环 + 日志需记录全文，压缩本无收益。`forwardHeaders.ts` 剥离客户端 `accept-encoding` 后由实例 defaults 统一补 identity。
- **上游代理**：`ServiceConfig.proxyUrl`（settings 键 `server.proxyUrl`，空串直连），仅对 https 上游生效——经 `https-proxy-agent` 走 CONNECT 隧道（兼容性优于 axios 原生 proxy 的 absolute-form）；http 上游多为本地调试直连。配置读 repo 缓存（写时失效），保存即生效（`service:saveConfig` 同时重启服务）；不支持 SOCKS5（axios 原生不涉，未引入 socks 依赖）。
- CORS 由中间件统一处理：预检 204 放行所有来源（服务自身有 Key 鉴权），其余响应 `setHeader` 放行来源，`proxyHandler.ts` 内不再逐响应补头。
- 请求头转发为黑名单剥离（`forwardHeaders.ts`）：只剥逐跳/传输头（host、content-length、connection 等，由 axios/http 自行生成）与 `authorization` / `x-api-key` / `cookie`（防本地 Key 泄漏给上游），其余原样透传；`authorization` 替换为上游 Key；`accept-encoding` 交给出站客户端自行协商。
- 流式透传消费 axios `responseType: 'stream'` 返回的 Node 流（async iterator 收窄为 Buffer + 背压写），abort 时销毁上游流终止循环。
- `proxyHandler.ts` 只依赖 `node:http` 类型（`IncomingMessage & { body?: unknown }`），不 import express 类型；框架类型只存在于 `proxyRouter.ts`。
- `proxyServer.ts` 用 `createProxyApp().listen(port, '127.0.0.1')` 拿到 `http.Server` 句柄，`close` + `closeAllConnections` 的关闭语义不变。
