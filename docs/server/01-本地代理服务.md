# 本地代理服务

> 核心功能：监听 `127.0.0.1:<port>`，凭全局 API Key 对外提供三协议兼容服务（OpenAI Chat / Anthropic Messages / OpenAI Responses），按模型映射反向代理到上游提供商。代码在 `src/main/src/server/`（Express 5；出站统一为 axios，实例与拦截器在 `upstream/httpClient.ts`；CORS / 鉴权 / 路由组装在 `app.ts`；每个路由一个文件在 `routes/`；协议差异由 `strategies/` 双向编解码策略消化，见 [02-协议适配与转换.md](./02-协议适配与转换.md)）。

## 目录结构（2026-09-19 重构：每路由一文件 + 策略 = 双向编解码器）

```

├── index.ts                  # 服务生命周期：start/stop/restart/status + 状态广播
├── app.ts                    # createProxyApp：CORS → 鉴权 → 挂载路由 → 404/错误兜底
├── respond.ts                # sendJson / sendOpenAiError / errMsg（OpenAI 信封，全局拦截用）
├── routes/                   # 每个路由一个文件

│   ├── chatCompletions.ts    # POST /v1/chat/completions（entry = openai）
│   ├── messages.ts           # POST /v1/messages（entry = anthropic）
│   ├── responses.ts          # POST /v1/responses（entry = openai-responses）
│   └── listModels.ts         # GET /v1/models
├── strategies/               # 协议策略（双向编解码器），接口与矩阵见 02 文档
│   ├── types.ts              # ProtocolStrategy 双向接口、RequestContext、EntryEncoder、UpstreamDecoder
│   ├── conversation.ts       # 统一会话 / 流事件 / 完成结果 / 用量（协议中性枢纽）
│   ├── registry.ts           # providerProtocol → 策略（唯一注册点）
│   ├── forward.ts            # 分发：同协议透传 / 异协议转换
│   ├── passthrough.ts        # 同协议 raw 直通（泛化：任意协议对自己的透传）
│   ├── converted.ts          # 异协议转换流（入口 codec ↔ 上游 codec）
│   ├── sse.ts / wireCapture.ts  # SSE 解析、线上口径捕获（策略间共享）
│   ├── openaiChat/           # 五件套：parse / encode / request / decode / index
│   ├── anthropicMessages/    # 同上
│   └── openaiResponses/      # 同上
├── upstream/
│   ├── httpClient.ts         # axios 实例（代理/错误增强拦截器）
│   ├── forwardHeaders.ts     # 请求头黑名单透传
│   └── urls.ts               # baseUrl 规范化与端点拼接（端点路径由策略提供）
└── logging/
    └── requestLog.ts         # startRequest/recordRequest 日志与用量门面、脱敏、parseClientName
```

## 生命周期

- 启动：`main/index.ts` `whenReady` 中 `ensureServiceDefaults() → await startProxyServer() → initQuota() → registerAppTray() → startSchedulers()`（服务开关关闭时只更新状态、不监听）。日志清理与启动收口已并入 scheduler（见 `../app/13-定时任务.md`）。
- 重启：渲染层「服务设置」保存端口/开关后，`serviceIpc` 的 `service:saveConfig` 内调用 `restartProxyServer()`。Key 变更无需重启（配置读 `settingRepo` 缓存、写时失效，保存即生效）。
- 退出：`app.on('will-quit')` → `stopSchedulers()` + `stopProxyServer()`（`close` + `closeAllConnections`）。
- 端口占用（EADDRINUSE）不崩溃，状态置 `error` 并广播。

## 状态推送

`server/index.ts` 的 `updateStatus()` 在状态变化时 `BrowserWindow.getAllWindows().forEach(w => w.webContents.send('server:status', status))`；渲染层经 `window.preload.service.onStatusChanged(cb)` 订阅（通道 `server:status`，载荷 `ServiceStatus`）。

## 请求处理流程（`app.ts` 组装，`routes/` + `strategies/` 处理）

```
OPTIONS            → CORS 中间件直接 204 + 预检响应（其余响应统一 setHeader 放行来源）
鉴权中间件失败     → 401 OpenAI 信封 + 记日志（全局拦截在协议路由之前）
GET  /v1/models            → routes/listModels.ts：本地生成 {object:'list', data:[…]}（启用且未归档的映射，且所属提供商未归档；owned_by=提供商名）
POST /v1/chat/completions  → entry=openai           → routes/entry.ts 校验 → 分发
POST /v1/messages          → entry=anthropic        → 同上
POST /v1/responses         → entry=openai-responses → 同上
其余 method/path   → 404（OpenAI 信封）
```

中间件顺序：CORS → 鉴权 → 路由（`app.get('/v1/models')` + 三条 `app.post(…, express.json(...))` 共享 32MB 上限）→ 404 兜底 → 错误兜底中间件。转发路由的异常经 `.catch(next)` 进入错误兜底，任何分支都不向客户端抛异常。

1. **鉴权**：兼容 `Authorization: Bearer <key>` 与 `x-api-key` 两种头；Key 来自 `settingRepo.getServiceConfig()`（模块级缓存，写时失效）。鉴权仍排在 `express.json` 之前（不为未鉴权请求解析 32MB 正文），但失败分支**有界读取客户端正文**（上限 1MB、兜底 2s，读完即回 401）——把 `model`/`stream` 与正文前缀写进日志行、`error` 记鉴权头**形态与长度**（不落 Key 内容）；否则这一行只剩状态码与客户端，排查不出是哪个模型、哪个客户端配错了 Key（2026-09-23）。
2. **映射与拦截**（`routes/entry.ts` 工厂，三个入口共用）：body 非对象 → 400；缺 `model` → 400；`modelRepo.findRoutes(publicName)` 一次联表返回该对外名下的**全部渠道** `MappingRoute[]`（同一对外名的多行即一个渠道组，见 `../app/15-负载均衡与故障转移.md`；**带写时失效缓存**——模型/提供商任一写操作后整体失效，见 `../data/01-数据模型.md` repo 清单）。**全部渠道都归档**（自身或所属提供商归档）→ 404 `model_archived`（明确告知，归档是对客户端的正式下线宣告）；**没有任何可用渠道**（全部禁用）→ 404 `model_not_found`（不泄漏配置）。**路由内的 400/404/503 按入口协议信封返回**（见 02 文档「错误信封」）。
3. **选路**（`server/balancer/`，2026-09-23 起）：读 `router.balancing` 配置 → 会话亲和取 key（请求头 / 协议元数据 / 消息指纹）→ `orderCandidates()` 按可用度排出尝试顺序（剔除额度阻断；低可用度且已断流的渠道优先放一次探针；绑定渠道排第一）。**全部候选被额度阻断 → 503 `all_channels_unavailable`**（逐渠道原因），不把请求送给已知没额度的渠道；总开关关闭时退化为单渠道直连（不选路/不拦额度/不改道）。
4. **转发分发与故障转移**（`strategies/forward.ts`）：`entry = strategyOf(入口协议)`，`upstream = strategyOf(route.providerProtocol)`（**按渠道各自的协议**判定，一次请求的多个候选可以混协议）——同协议 → `passthrough.ts` raw 直通；异协议 → `converted.ts` 经统一会话转换（会话解析只做一次）。执行器返回 `AttemptOutcome`（是否已提交、归类、供日志的线上报文、未提交失败的回放闭包），由循环决定改道还是收口：**只在尚未向客户端写出任何字节时改道**，最多 `maxAttempts` 个渠道；失败按归类扣减/阻断该渠道可用度（见 `../app/15-负载均衡与故障转移.md`）；一次客户端请求**只落一条日志** + `retry_trace` 记录被改道掉的尝试。
5. **透传（同协议）**：`getUpstreamClient().post(joinEndpointWithQuery(baseUrl, upstreamPath, 原 query))`（axios，`validateStatus` 全放行使非 2xx 也走正常透传）；**除 `model` 字段替换外请求体原样透传**；客户端请求头全量透传（`upstream/forwardHeaders.ts` 黑名单剥离），鉴权与协议头由 `upstreamAuthHeaders()` 替换/追加（openai/responses：`authorization: Bearer 上游Key`；anthropic：`x-api-key` + `anthropic-version`）；流式原样逐块回写（drain 背压 + close 兜底），usage 经上游协议解码器「抽头」收集（事件不回写）；非流式读全量原样返回、`decodeResponse().usage` 提取用量。客户端断开 → abort 上游，请求阶段抛错 / 流阶段销毁，日志记 499。
6. **转换（异协议）**：`entry.parseRequest` → `upstream.buildRequest`（出站报文即线上捕获）→ axios → 非 2xx 读全量错误体按真实状态码 + 入口信封包裹摘要 → 流式经「上游解码 → 统一事件 → 入口编码」回写（惰性响应头）；非流式为**真·非流式上游请求**（stream:false），读全量 JSON → `upstream.decodeResponse` → `entry.encodeCompletion`。协议逐字段映射见 [02-协议适配与转换.md](./02-协议适配与转换.md)。
7. **全量采集与落库（两阶段）**：入口生成 `requestId`（UUID）；`path` 记**上游实际请求路径**（`baseUrl` 的路径前缀 + 端点 + 透传保留的 query，经 `upstreamPathOf()` 取 pathname+query；本地拦截无上游时记客户端入口路径）。**采集口径为「线上口径」：请求正文/标头 = 实际发给提供商的内容，响应正文/标头 = 提供商实际返回的内容**（流式正文为全部 SSE 文本，边读边累积不截断；标头入库前脱敏）。**本地拦截行例外（2026-09-23）**：401/400/404/503 与转换路径的会话解析失败都没发起上游请求，请求侧改记**客户端入站正文**（401 走有界读取、可能截断并在 `error` 注明；其余分支用已解析的请求体直接序列化），main 侧以 `local` 标记与转发行区分。
   - **开始阶段**（路由命中、请求上游**之前**）：`logging/requestLog.startRequest()` → `logRepo.startLog()` 落一条 **pending 行**（`finished_at`/`status`/`duration_ms` 为 null），日志页据此立即显示「进行中」并实时计时。`stream` 先按客户端意愿预估，结束时以实际上游 content-type（透传）或实际下发形态（转换）回填。
   - **结束阶段**（成功 / 失败 / 客户端断开）：统一调 `recordRequest()`，以 `request_id` 为冲突键 upsert 回填状态码、耗时、token 与响应正文标头，**并按状态码累加 `usage_daily` + `usage_hourly`**（请求数与耗时不分成败，token 仅成功请求计入，详见 `../app/04-统计看板.md`）；非 2xx 时响应前 500 字符入 `error`。
   - **同步拦截分支不落 pending**：401 / 400 / 404 / 503 直接由 `recordRequest()` 单次写入（upsert 退化为 INSERT），未知字段填 `-`；这类行标 `local: true`（本地拦截），正文是入站口径。502（上游网络失败）因已过 `startRequest`，走回填。
   - **来源客户端**：入口用 `parseClientName(req.headers['user-agent'])` 把 UA 归一为 `client` 列——取首个空白分隔 token 的第一个 `/` 之前的部分，只留名称不留版本且保留原大小写；无 UA 记 null。**所有分支**（含 401/400/404 拦截）都会落库。日志页「来源」列、筛选与首页「来源 Agent 请求数」柱状图读这一列（见 `../app/04-统计看板.md`）。
   - 提供商未返回用量时一次性兜底估算：按**出站**请求正文估算 token（CJK 1 字 1 token、其余 4 字符 1 token）计入 `unrecognized_tokens` 并作为总计；**本地拦截行（`local`）跳过估算**——它们没出云，按入站正文估算会凭空产生 token 污染统计。落库失败静默，不影响代理。
   - 应用退出 / 崩溃残留的 pending 行由启动时 `markPendingInterrupted()` 收口为 499「服务中断」，详见 `../data/01-数据模型.md`。

## 日志变更推送（日志页实时刷新）

`logRepo` 落库 / 回填后触发写入观察者 `onLogWritten`，`logIpc.ts` 订阅后经 **300ms 合并广播** `log:changed`（无载荷）到 `BrowserWindow.getAllWindows()`（与 `server:status` 推送一样，发送前先查 `isDestroyed()`）；渲染层用 `window.preload.log.onChanged(cb)` 订阅，日志页收到后 300ms 防抖重查，仅在「自动刷新开启 && 第 1 页 && 窗口可见」时才真正取数。30 秒轮询保留为兜底（推送丢失、窗口从后台恢复），同样只在窗口可见时触发且走静默刷新。

## 错误格式

**全局拦截**（`app.ts`，协议路由之前：401 鉴权、413 超限、未知路由 404、兜底 500）统一 OpenAI 风格；**路由内错误**（body 非法 400、缺 model 400、模型 404、转换路径上游错误）按**入口协议**信封（openai / anthropic / responses 三种形态见 [02-协议适配与转换.md](./02-协议适配与转换.md)「错误信封」）。所有响应带 `access-control-allow-origin: *`。

| 场景 | 状态码 | 说明 |
|------|--------|------|
| Key 错误 | 401 | 全局，OpenAI 信封 `invalid_api_key`；日志行记 `model`/正文前缀，`error` 为 `invalid api key · 鉴权头: …`（头形态 + 长度） |
| body 非 JSON / 缺 model | 400 | 入口协议信封 |
| body 超 32MB | 413 | 全局，OpenAI 信封 |
| 模型未映射/禁用 | 404 | `model_not_found`；归档 → `model_archived`（入口协议信封） |
| 上游网络失败 | 502 | message 与日志 `error` 为拦截器增强后的具体原因（`底层原因: 中文提示`，映射表见 `upstream/httpClient.ts` `NETWORK_HINTS`）；首字节超时（60s 无响应头）同归此类 |
| 全部渠道被额度阻断 | 503 | `all_channels_unavailable`，message 列出每个渠道的阻断原因（入口协议信封） |
| 转换路径上游流提前中断 | 502 | `Upstream stream ended unexpectedly` |
| 客户端断开（已 abort 上游） | 499（仅日志，不回写） | — |
| 请求进行中（仅日志，pending 行） | `status` 为 null | — |
| 应用退出残留的进行中请求 | 499（启动时由 `markPendingInterrupted()` 标记） | — |
| 上游返回（透传） | 原样透传上游状态码与 body | — |
| 上游返回（转换） | 真实状态码 + 入口信封包正文前 300 字摘要 | — |

body 超 32MB / 非法 JSON 由 `express.json` 抛错（413 / 400），错误兜底中间件统一转 OpenAI 风格；非对象 body（数组/标量）在 `routes/entry.ts` 内拦截为 400。

## 注意事项

- **无请求总超时，但有首字节超时（2026-09-23）**：长流式回答不设上限（axios `timeout: 0`），靠客户端断开驱动 abort；`postUpstreamStream()` 另挂 60s 独立计时器，**拿到响应头即清除**（axios 的 `timeout` 是 socket 空闲计时，会在大模型思考停顿期间误杀长请求，故不直接用），超时归类为网络错误 → 扣可用度 + 改道。该超时**只中断本次尝试**：每次调用另建 attempt 级 controller，调用方传入的请求级信号只被监听、不被 abort（拿它去 abort 会把整个请求永久判成「客户端已断开」，后续改道立刻以 `client aborted` 失败且客户端收不到任何响应）。
- **出站统一走 `upstream/httpClient.ts`**：axios 实例按 `proxyUrl` 缓存重建（连接复用），`proxy: false` 屏蔽 `HTTP_PROXY` 等环境变量干扰；**响应拦截器统一增强网络层错误**（「错误码: 底层 cause 原因: 中文提示」），三条转发路径 catch 到的都已是具体原因。
- **出站固定 `Accept-Encoding: identity`（禁用上游压缩）**：axios 在 `responseType: 'stream'` 下不解压 gzip，压缩响应会以乱码入库并原样发给客户端；禁用后响应体/响应头均为提供商原样明文，日志记录、客户端透传、SSE 解析才都成立。
- **上游代理**：`ServiceConfig.proxyUrl`（空串直连），仅对 https 上游生效——经 `https-proxy-agent` 走 CONNECT 隧道；配置读 repo 缓存、保存即生效；不支持 SOCKS5。
- CORS 由中间件统一处理：预检 204 放行所有来源，其余响应 `setHeader` 放行来源，策略层内不再逐响应补头。
- 请求头转发为黑名单剥离：只剥逐跳/传输头与 `authorization` / `x-api-key` / `cookie`（防本地 Key 泄漏）；透传路径鉴权头由 `upstreamAuthHeaders()` 替换；转换路径 `content-type` / `accept` 剥离后由协议自建。
- 路由 handler 只依赖 `node:http` 类型，不 import express 类型；框架类型只存在于 `app.ts`。
- `server/index.ts` 用 `createProxyApp().listen(port, '127.0.0.1')` 拿到 `http.Server` 句柄，`close` + `closeAllConnections` 的关闭语义不变。
- **新增入口路由**：`routes/` 建一个文件（`createEntryHandler('协议')` 一行）+ `app.ts` 挂载；**新增上游协议**：`strategies/` 建五件套目录 + `registry.ts` 注册。
