# 负载均衡与故障转移

> 2026-09-23。**动机**：同一个模型可能同时订阅了两家（例如 OpenCode Zen 与 Command Code 都提供 deepseek-v4.1-flash），
> 对外只该暴露一个模型名，由本机按渠道的健康度与额度自动分流。这是代理的**核心引擎**：
> 它决定「这个请求发给谁」，也决定「谁现在还能收流量」。

一句话架构：**可用度（0~100）= 路由权重**。失败按「先大后小」扣、成功按「先小后大」涨、额度耗尽直接归零、
额度恢复直接拉满；同一会话固定同一渠道；只在「还没向客户端写出任何字节」时改道。

---

## 一、数据模型：一个对外名 = 一个渠道组

`models` 表**沿用不拆表**，同一 `public_name` 的多行即一个渠道组（负载均衡的候选集）：

| 概念 | 落点 |
|------|------|
| 对外模型名（组） | `models.public_name`（同名多行即一组） |
| 渠道 | `models` 的一行 = (提供商, 上游模型名) |
| 组的启停 / 归档 / 改名 | 对该名下**全部行**的单事务批量写 |
| 渠道的启停 / 归档 / 编辑 | 单行写（原有语义不变） |

**为什么不做「对外模型表 + 渠道表」两张表**：那样会出现「有对外名却没有渠道」的空组，得靠守卫拦住
「不要对外开放」；而名字由渠道行承载时，**没有行就没有这个名字**，这条不变量由结构直接保证。
另一个好处是迁移无损：只需去掉 `public_name` 的唯一约束（0007 迁移四句话），历史表的 `model_id`
语义（渠道 id）与改名跟随（`renameRepo` 按 id 圈定）一行都不用改。

约束与守卫（`modelRepo.ts`）：

- `idx_models_public`（普通索引）：路由热路径按对外名取该名的全部渠道
- `idx_models_channel` **unique(public_name, provider_id)**：一个提供商在同一对外名下只允许一条渠道，
  **含归档行**——归档同样占用该组合，与「归档行占用名字」的既有口径一致
- `ensureChannelAvailable()`：撞活跃行 → 「该提供商已有对外名的渠道」；撞归档行 → 「请先在已归档列表中恢复」
- `ensureGroupUsable()`：该名下存在行且**全部归档** → 拒绝再挂渠道（先恢复或改名）

组级动作（`model:groupRename` / `groupEnabled` / `groupArchive` / `groupRestore`）：

- **改名**：一次改该名下全部行，并对每个渠道行 id 各调一次 `applyModelRename`
  （聚合表按 `(桶, 供应商, 对外名)` 主键 ON CONFLICT 合并、日志表按 `model_id` 圈定，同事务内互不干扰）；
  组名不能改成另一个已存在的组名——同名合并会让「这条历史属于哪个组」失去答案
- **启停**：只作用于未归档行（归档行冻结）。注意口径：某渠道被单独停用后，组级「关闭 → 打开」
  会把它一并启用（不记单独状态）
- **归档 / 恢复**：归档只归档未归档行；恢复恢复该名下**全部**行（同上，组内不保留单独归档状态）

对外表现：`GET /v1/models` 按 `public_name` 去重（`createdAt` 取组内最早；多渠道的组 `owned_by` 记 `ai-router`，
单一渠道仍记提供商名）；请求命中时若该名全部行都归档 → 404 `model_archived`，有一行可用即正常转发。

## 二、可用度模型（`server/balancer/health.ts`）

每个提供商（键 = `providerId`）维护一个 0~100 的运行值，**它就是路由权重**。
状态在内存里（`Map<providerId, ChannelHealth>`），懒初始化（首次出现即满值）。

| 事件 | 计算 | 效果 |
|------|------|------|
| 上游失败 | `avail ← max(1, avail − max(2, avail×0.1))` | 100→90→81→73…（**先大后小**，26 次左右到 1，**永不归零**） |
| 请求成功 | `avail ← min(100, avail + max(2, avail×0.1))` | 1→3→5…（**先小后大**，约 27 次回到 100） |
| 额度耗尽 | `avail ← 0`（另记 `blockReason` / `blockUntil`） | 直接不给流量（0 只由额度阻断产生） |
| 额度恢复 | `avail ← 100`，清阻断 | **直接拉满**，不逐点回涨 |

采样曲线（另一个渠道恒为 100 时，本渠道的流量占比）：

| 连续失败次数 | 0 | 1 | 3 | 6 | 10 | 16 | 22 |
|---|---|---|---|---|---|---|---|
| 可用度 | 100 | 90 | 73 | 53 | 35 | 19 | 10 |
| 分到的流量 | 50% | 47% | 42% | 35% | 26% | 16% | 9% |

改造口径：**开始只挪一点点流量**（一次失败只从 50% 挪到 47%），失败越多占比越低；「永不归零」是为了给
自动恢复留入口——归零就只有额度阻断这条硬状态才配。

### 探针（自愈的关键一环）

可用度掉到个位数后，按权重它几乎拿不到请求，**没有成功事件就永远涨不回来**——自动恢复会变成死锁。

规则：`可用度 ≤ 40` **且**距上次被派发请求超过 `30s`（说明这条渠道已经没有流量了）时，本次请求优先交给它试一次，
成功即按上表回涨。同一渠道 30 秒内最多一次探针，探针在**选择时**就打上 `lastAttemptAt` 标记，
所以并发请求不会形成探针风暴。额度阻断（可用度 0）的渠道不参与探测——那是不许给流量的硬状态。

探针只在**没有亲和绑定**的请求上生效（见第三节）：绑定会话优先走绑定渠道，否则探针会把活跃会话
从绑定渠道上拽走，白丢一次 cache 命中。降级渠道的自愈入口因此收窄到未绑定流量上。

### 失败归类（`server/balancer/classify.ts`）

| 情形 | 扣可用度 | 改道下一渠道 |
|------|---------|-------------|
| 网络错误 / 连接失败 / 首字节超时 | ✓ | ✓ |
| 5xx / 529 / 429（正文无额度关键字） | ✓ | ✓ |
| 401 / 403 | ✓ | ✓（另一家可能凭据正常） |
| 402，或 4xx/5xx 正文含额度关键字 | ✓ + **直接额度阻断**（TTL 10 分钟） | ✓ |
| 404（上游没有该模型 / 端点） | ✗（配置问题，不是渠道不健康） | ✓ |
| 400 / 413 / 422 等请求侧错误 | ✗ | ✗ 原样回给客户端 |
| 2xx 但首 token 前断流 | ✓ | ✓ |
| 2xx 流中失败（已提交） | ✓ | ✗ 改不了道 |
| 客户端主动断开 | ✗ | ✗（记 499） |

额度关键字（正文命中即按额度处理）：`insufficient_quota` / `quota exceeded` / `out of credit` /
`insufficient balance` / `payment required` / 欠费 / 余额不足 / 额度不足 / 额度已用尽 / 免费额度已用尽。
宁可误阻断 10 分钟，也不把请求继续送往缺额度的渠道（阻断到期会自动解除并拉满 = 放一次全量探测）。

**分界只有一条**：上游服务 / 凭据 / 额度的问题要扣分并改道；请求本身的问题不扣分也不改道
（把 400 当成渠道故障，一次参数写错就会把所有渠道一起拉黑）。

## 三、会话亲和（`server/balancer/session.ts`）

同一会话固定同一渠道，为的是保住上游的 prompt cache 命中率（在两家之间来回切等于每次冷启动）。

标识按三段兜底取值，**不同来源加前缀隔离**（`h:` / `b:` / `m:` / `fp:`）：

1. 请求头：`x-session-id` / `x-conversation-id` / `session-id` / `x-claude-code-session-id`
2. 请求体字段：`prompt_cache_key`（Codex / Responses）、`session_id`、`conversation_id`
3. Anthropic `metadata.user_id`（Claude Code 形如 `…_session_<uuid>`，取 `session_` 段）
4. 兜底**消息指纹**：`sha1(首条 system 文本 + 首条 user 文本)` 前 20 位

第 4 段是为**不发会话 ID 的客户端**（opencode 之类）准备的：一次会话里这两段是稳定的（后续轮次只是追加消息），
不同会话几乎不会撞；即使撞上也只是两条会话共用渠道，没有副作用。上下文压缩改写首条消息时会重新绑定。
取样只取前 1000 字符、只看前 8 条消息，避免在大 body 上做全量遍历。

绑定表是 `lru-cache`（max 2000、ttl 2 小时、`updateAgeOnGet` 活跃续期），键是**对外模型名 + 会话标识**：
同一会话混用多个对外名（如 opus + haiku）时各走各的绑定，否则两条模型会互相把绑定翻来翻去
（翻到不属于当前候选的那个，`find` 落空 = 亲和静默失效）。规则：

- 绑定的渠道仍在候选里（未阻断 / 未停用 / 未归档）→ 排第一（**优先于探针**），其余候选照常按可用度排
- 绑定渠道失败改道成功后 → **重新绑定**到实际服务的渠道
- 渠道被额度阻断或停用 → 绑定自动弃用，按权重重选

**可观测性**：绑定表只在主进程内存里，日志页看不到会话标识——`request_logs` 的请求标头记的是**出站**
标头，客户端专有的会话头不透传上游就不会出现（正文里的 `metadata.user_id` / `prompt_cache_key` 倒是能看到）。
唯一观测点是主进程 `[balancer]` 行，**每请求一行**：

```text
[balancer] deepseek-v4.1-flash → OpenCode Zen（状态 200）· 会话 fp:3f2a1b8c9d0e1f2a3b4c
```

指纹是不可逆哈希、直接给全 20 位；`h:` / `b:` / `m:` 是客户端原始标识，只留前 8 位。连着几条请求
看会话键是否稳定，即可判断亲和是否命中。

**取舍**：绑定会话在渠道「降级但仍可用」时不会主动迁移（流量迁移发生在**新会话**与**失败改道**上）。
这是有意的——迁移会牺牲 cache 命中率，而可用度衰减已经让新会话显著偏向健康渠道；探针也只服务未绑定会话，
不会来拽走绑定渠道上的流量。真要立刻切断的只有额度阻断（硬状态，绑定直接失效）。

## 四、重试与「提交」语义（`strategies/forward.ts`）

只在**尚未向客户端写出任何字节**时改道，最多尝试 `maxAttempts`（默认 3）个渠道。
为此两个执行器的提交时机都往后挪：

- **透传**（同协议）：非 2xx 先读全量错误体缓冲、不立即回写；2xx 流式响应的**响应头推迟到首个数据块到达**时才写
  （「200 但一个字都没吐就断了」也能改道）
- **转换**（异协议）：入口编码器本来就是惰性响应头（首次写事件才 `writeHead(200)`），判据用 `encoder.headWritten`
- 已经提交后的一切失败维持原样：透传路径断流、转换路径按入口协议写流内错误帧，都不再重试
- 客户端断开：请求级 `AbortController` 中断正在进行的上游读取，记 499，不扣分不改道

会话解析（异协议路径）在循环外**只做一次**并复用；候选渠道可以混协议（每个渠道按自己的协议选透传还是转换）。

### 日志口径：一次客户端请求只落一条

改道不额外产生日志行，**用量统计不会因为重试而虚增**：

- 主行记**最终渠道**的线上口径（请求报文、响应正文/标头、状态码、token）
- 新增列 `request_logs.retry_trace`：未提交即失败、被改道掉的尝试，形如
  `[{ provider, status, error, at }]`（`status` 为上游真实状态码，网络层失败为 `null`）
- `error` 字段为最终结果摘要；透传路径非 2xx 的 `error` 现在带 `Upstream request failed with status N:` 前缀
  （与转换路径统一，早前只有正文片段）
- 日志详情页展示为「渠道重试轨迹」分区
- 主进程 `[balancer]` 行：**每请求一行**（最终渠道 + 状态 + 重试次数 + 会话键，形如
  `→ OpenCode Zen（状态 200，重试 1 次）· 会话 fp:3f2a1b…`），改道时循环内另有一行（谁失败、改道到谁），
  两行都带会话键；`[balancer]` 行与 `retry_trace` 是两个观测面，前者在终端、后者在日志页

### 首字节超时

出站 axios 的 `timeout` 一直是 0（长请求不被掐断），代价是**上游挂死时无限等待且没有降级**。
现在由 `upstream/httpClient.postUpstreamStream()` 统一处理：另挂一个 60s 的独立计时器，
**拿到响应头立即清除**（axios 的 `timeout` 是 socket 空闲计时，会在大模型思考停顿期间误杀长请求，
所以不能直接用）。超时归类为网络错误 → 扣分 + 改道。

**中断信号按尝试隔离**：调用方传进 `postUpstreamStream()` 的是「客户端断开」的请求级信号，函数只监听它，
另建 attempt 级 controller 交给 axios，超时只中断这一次尝试。反过来拿请求级信号去 abort 会让整个请求
永久处于「已断开」：后续改道会立刻以 `client aborted` 收场（不扣分也不可改道），失败响应一个字节都
回不到客户端，客户端只能等到自己超时——这正是「上游挂死 → 降级」这条链路要避免的结果。
对应的，改道判定同时要求 `!controller.signal.aborted`：客户端已断开时不再发起注定失败的上游调用。

## 五、额度前置拦截（`server/balancer/quotaGuard.ts`）

**这一半是「不等请求失败再降级」**：余量定时刷新（10 分钟一轮，见 `13-定时任务.md`）落库后即时判定，
把额度已用尽的渠道可用度压到 0，请求根本不会发给它（上一轮 11-余量查询.md 的快照，本轮有了第一个下游消费者）。

判定口径（全读快照，零出站）：

- 任一窗口（primary / secondary / tertiary / extraWindows）`usedPercent >= 100` **且未到 `resetsAt`** → 阻断，
  解除时刻取该窗口的重置时间；`resetsAt` 已过说明窗口已重置（快照是上一窗口的旧值），不视为耗尽
- `cost.balance <= 0` → 阻断（余额型：DeepSeek 没钱的场景），解除时刻取 `cost.resetsAt`
- `cost.limit > 0 && cost.used >= cost.limit` → 阻断

阻断状态机（`health.applyQuotaBlock`）：

| 来源 | 建立 | 解除 |
|------|------|------|
| 快照（权威） | 判定为耗尽 → `avail = 0` + 原因 + `blockUntil = resetsAt` | 下一次快照显示健康；或 `blockUntil` 到点自动解除（窗口重置不必等下一次刷新）；兜底 `queriedAt + 60min` 防配额接口长期不可用卡死 |
| 响应推断（启发式） | 402 / 额度关键字 → `avail = 0`，TTL 10 分钟 | TTL 到点自动解除并拉满（等于放一次全量探测）；若仍缺额度会再次被请求打回阻断 |

- **快照查询失败时不改状态**：无信息不等于健康，不该解除已有阻断
- 阻断到期是**惰性判定**（`availabilityOf` 里比较时间），不需要为「窗口重置」单独排定时器
- 启动时 `syncQuotaBlocks()` 用落库快照重建阻断——否则重启后可用度全回 100，头几个请求会被送去没钱的渠道
- 设置页总开关关闭时不作判定，并解除已有阻断

**全部候选都被阻断 → 直接 503**（`all_channels_unavailable` + 逐渠道原因），不做「忽略阻断硬试」：
把请求送给已知没额度的渠道，正是这条链路要避免的事。

## 六、配置、IPC 与界面

### 配置（settings 键 `router.balancing`）

```ts
{ enabled: true, sessionAffinity: true, quotaGuard: true, maxAttempts: 3 }
```

- `enabled`：总开关。关闭 = 单渠道直连（不选路、不拦额度、不改道），其它三项一并失效
- 契约在 `@common/types/balancer.ts`，解析统一走 `@common/utils/balancerConfig.parseBalancerConfig`
  （主进程读库与设置页读设置**同一口径**，界面显示的就是引擎跑的）；`maxAttempts` 钳制在 1~5
- 比例类常量（0.1 / 最小步进 2 / 下限 1 / 探针阈值 40 / 冷却 30s / 首字节超时 60s / 阻断 TTL / 会话 TTL）
  **写死在 `server/balancer/config.ts`**：它们定义的是上面那套曲线本身，改了就不是同一套行为

### IPC / 桥 / 契约

| 通道 | 说明 |
|------|------|
| `model:groupRename` / `groupEnabled` / `groupArchive` / `groupRestore` | 组级动作（`model:create/update/archive/restore` 仍是渠道级；`update` 不再接受 `publicName`——名字不属于渠道） |
| `balancer:states` | 全部未归档提供商的健康快照（可用度 / 状态 / 阻断原因与解除时刻 / 连续失败 / 最近成功失败时刻），联表补提供商名 |
| `balancer:reset` | 手动把可用度拉回满值并清阻断（充值 / 修好 Key 之后不想等下一轮余量刷新的逃生口） |

### 界面

- **模型路由页（原模型映射页）**：顶部 `表格 | 链路` 分段切换（`t-radio-group` + `.fluent-segmented`，
  样式是全局的，与托盘面板同一套）。表格 = 管理，链路 = 观测
- **表格视图**：主表一行一个对外名（渠道数 / 组级健康徽标 / 组级启停开关 + `n/m` 启用计数 /
  重命名·归档·恢复），点开是渠道表（提供商 / 上游模型 / **健康徽标** / 启停 / 编辑·重置·归档·恢复 + 新增渠道）
- 健康徽标：`可用度 82`，色档 好=绿 / 衰减=黄 / 额度阻断=红，悬浮给出状态、阻断原因与解除倒计时、最近失败与失败时刻；
  渠道处于非正常状态时才出现「重置」按钮（稀有逃生口，不进常规操作路径）
- 健康快照按页面挂载期 5s 轮询（`pages/models/useChannelHealth.ts`，`useIntervalFn` 驱动、作用域销毁自动停；
  主进程内存态没有推送通道；读失败静默）。**轮询由页面独占**，两个视图共用同一份 Map，切视图不会变成两份 5s 查询
- 新增弹窗：对外模型名是 `t-auto-complete`（选已有名 = 往该组加渠道、输入新名 = 建新组），
  从某组展开区进来时锁定为该组名；提供商下拉自动剔除该组已占用的提供商

把内存里的路由状态画出来——否则整台引擎是个黑盒：

- **零新增 IPC**：渠道与分组取页面已加载的 `model.list()`，健康度取同一份 `balancer:states()` 的 Map，
  引擎开关读 settings 键 `router.balancing`（解析与设置页共用 `parseBalancerConfig`，并订阅 `setting:changed`
  使设置页改完切回立刻正确）
- **参与分流 = 引擎 `isUsable` 同口径**（渠道与提供商都启用且未归档）。被额度阻断的渠道（可用度 0）**照样画出来**
  并标红——那正是要回答的问题；停用 / 归档的不画，组内计数后以脚注说明「另有 n 个渠道已停用 / 归档」；
  整组无可用渠道（对外已归档，请求会 404）整条跳过
- **支线数字**：`可用度` 走 `ChannelHealthTag`（复用徽标与悬浮明细，不复制口径），`占 x%` 由
  `@common/utils/balancerDisplay.routeShares` 推算。占比 = 可用度在组内的权重占比，**等于该渠道被选为首次尝试
  渠道的概率**（`P(i) = w_i / Σw`，与 `weightedShuffle` 的不放回抽样同源），所以它直接回答「请求会发给谁」；
  页面文案同时声明它是**推算**值——会话亲和与探针会在此基础上产生偏移。全组被阻断时给出「请求会直接返回 503」
- **不标「首选渠道」**：`weightedShuffle` 每请求重掷，首位不稳定，标了就是假的
- **引擎关闭时报警示**（`t-alert` warning）：关闭后请求固定发给第一条可用渠道，此时链路图会骗人
- 折线用 **DOM + CSS** 画（首行竖线从行中心起、末行到行中心止，于是竖线正好贯通第一支到末支中心；
  主干到分叉点那条 14px 横线挂在容器 50% 高度上）：红线禁止手写 SVG，而链路形态用 border 折角比 SVG 更轻、
  更贴 Fluent 样式，也不必引入图表库。**等分行高是这套几何成立的前提**，故支线内容一律单行不换行

## 七、已知限制与取舍

- **健康度只存内存，不落库**：重启后可用度回 100（额度阻断由落库快照在启动时重建，
  所以「没钱了」不会在重启后漏放行）。代价是重启后可能有一两次请求打到刚出过问题的渠道。
  不落库的理由：这是秒级变化的短期健康度，写库频率会跟着请求量走，而重启重学的成本只有一次失败（−10）。
- **不做渠道静态权重**：默认等权，权重完全由可用度驱动（要 7:3 分流目前只能靠额度/失败自然形成）。
- **组级启停 / 恢复是批量写**：不记「某渠道曾被单独停用」这种中间状态（见第一节）。
- **探针会占用一次真实请求**：单条降级渠道每 30 秒最多一次，代价是那一次请求可能要多走一次改道。
- **绑定会话不随降级迁移，也不参与探针**：见第三节的取舍说明；探针只服务未绑定流量，
  所以某条降级渠道若被某会话长期绑定占用，它的自愈只能等未绑定请求出现。
- **绑定表按 (对外名, 会话) 计容量**：上限 2000 条、闲置 2 小时过期，同一会话用多个对外名会占多条。
  被淘汰只是重新掷一次骰子（可能换渠道 = 一次冷启动），没有正确性问题。
- **没有余量策略的提供商只能靠反应式衰减**：不绑策略就没有快照，额度耗尽只能等上游报错后按关键字推断
  （429 带额度关键字 / 402）。
- **429 的语义靠正文猜**：不区分「限流」与「额度用尽」时按限流处理（扣分 + 改道），不做硬阻断。
- **改道只在前缀阶段**：流已经开始后无法换渠道，客户端的观感与改造前一致（透传断流 / 转换写流内错误帧）。
